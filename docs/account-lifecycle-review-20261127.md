# Account lifecycle – read-only production schema review
2026-11-27. No production writes, no real-user deletion. Reviewed current repository and live public-schema columns, foreign keys and cleanup job metadata, not row contents or full security policies.

## Confirmed findings
- No dedicated account-deletion or data-export workflow identified by repository path scan. Existing Admin Center verifies staff access; player profile supports statistics, avatar removal, blocks, reports and suspension. Do not infer absence of every possible deletion mechanism from filenames alone.
- profiles.id references auth.users ON DELETE CASCADE. Deletion of auth user can cascade into profiles and other records; matches.player1_id/player2_id/winner_id/turn_player_id are NO ACTION references to profiles. Tournament owner and AI model-player references RESTRICT deletion. Other NO ACTION references include practice_matches.deleted_by, half_it_visits.player_id, sixty_one_visits.player_id, pentathlon room player/actor, exclusions, tournament archived_by and AI creator. Deleting blindly can fail, or destructive workarounds can erase other players' shared history.
- Tournament matches have player/winner references ON DELETE SET NULL; membership/group records can cascade. Preserve bracket integrity and distinguish actual bye/unknown from deleted player. Existing statistics depend on player identity.
- Avatar objects are in player-avatars via Storage API, with short-lived signed URLs; metadata cascades from profiles. Actual files must be removed via Storage API rather than SQL; owned objects can prevent auth deletion. 
- Reports and suspensions contain identity fields and snapshots, not all protected by cascading profile references. Free text, evidence, logs, practice state JSON, leaderboard names and backups need separate review. Pseudonymized identifiers can remain personal data.
- Active cron jobs verified successful on latest recorded run: dartarena-media-telemetry-retention, dartarena-issue-log-retention, dartarena-player-report-evidence-retention. The last two clear diagnostics/evidence rather than delete report records. Existing old backup schemas and backup/restore retention are unresolved.

## Proposed staged implementation – not activated
1. Privacy request intake: authenticated self-request with type (access, correction, erasure, other), minimal reason optional, receipt and state; staff access restricted to authorised personnel, no public listing; avoid collecting unnecessary identity documents. Owner-only review of deletion with Admin/Owner role rules defined separately. Add rate limits, anti-duplicate constraints, actor audit, and retention plan. Do not add a request button that claims success before backend exists. Provide a working contact channel first.
2. Read-only deletion impact preview: authorised server endpoint, validate target and permissions, count references and storage objects by category; no PII dumps. Flag active matches, current tournament ownership, protected roles including last Owner, linked moderation and unresolved retention. Never change data in preview. Recheck before any execution.
3. Decide retention/anonymization policy: remove private profile/auth details where required, preserve other players' records only with documented basis and minimal identity. Avoid a universal placeholder player that merges statistics or violates match constraints; design retired identities or immutable snapshots only after testing. Explicitly map all direct and indirect relations and JSON/name copies; include old backups, logs and processor deletion.
4. Implement server-side deletion orchestration only after backup/restore test and explicit owner approval. Confirm authenticated request and authority, safely close active play, handle tournament ownership, prevent new sessions and writes, delete Storage API objects, process data under approved policy and delete Auth via trusted server. Verify session invalidation: existing JWTs may remain usable until expiry; design live session/account checks where needed. Use retryable state, transactional steps where possible, explicit partial-failure reporting. Never expose service role in client. No bulk delete or production test using a real account.
5. Test disposable fixtures: ordinary player, active match, owned tournament, protected owner, opponent statistics, reports, avatars, backup references, repeated request, stale JWT, role bypass, concurrent play and deletion, storage failure, partial failure, rollback/restore, actual deletion vs pseudonymization. Test UI separately. Then decide release.
6. User administration: privacy requests separate from disciplinary reports, distinguish suspensions from deletions, show request status and justified decisions, prevent self/last-Owner deletion through staff controls. No new privileges until reviewed.

## Blockers
Operator name/contact, age policy, retention decisions, data mapping/processor contracts, verified backup and restore (not yet available), and safe anonymization/statistics design. No automatic account deletion or new UI enabled by this document.
